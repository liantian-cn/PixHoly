# 烈日奶骑五人小队迁移分析

分析日期：2026-09-30。交付范围：还原《烈日奶骑队伍.json》的执行语义，评估迁移到 PixHoly 的数据、像素协议和模块改动。本次只新增本文，不修改 JSON、Shigure、Lua 插件或 Python 循环。下文的“建议”是待后续实施确认的迁移方案，不代表已实现或已在游戏内验证。

## 1. 结论与证据基线

这份配置可以作为五人奶骑循环的业务参考，但不能只把 40 条条件翻译成 Python。它依赖 Shigure 的队伍有效性、治疗吸收折算、读条治疗预测、动态阈值、技能索引转换和宏目标映射。PixHoly 目前仍是铸光防骑实现，主要缺口在队伍数据和友方目标动作，而不是截图或键盘框架。

迁移应保留单项目、单专精、单循环、单配置。建议复用 PixHoly 的截图、Matrix、顺序 Action worker 和键盘驱动，手写奶骑决策；不引入 Shigure 的通用 JSON 解释器、模块编辑器或 40 人宏展开系统。

优先解决五件事：

1. 明确“队伍生命值”的计算口径，保留治疗吸收对选人和计数的影响。
2. 将玩家及 party1–4 的有效性、血量、职责、驱散和射程传给 Python。
3. 统一驱散和药水的“判定对象—实际动作”，修复依赖中的名称、ID 和宏文本不一致。
4. 保留原规则顺序作为基线，单独评审施法保护、移动判断、群疗与填充输出的优先级。
5. 首领特例和插入技能单列扩展阶段，不把未验证的数据接口放进首版必需链路。

### 1.2 当前 Shigure 不能直接等价运行此文件

`ModuleStore.HasCompatibleVersion` 要求模块版本与应用版本完全一致，因此原文件在当前版本中会被排除出运行选择。更改版本字符串也不能完成迁移：当前 `ModuleUnit` 已用 `FilterGroups / TargetField / SelectionMode / ValueName` 替换旧字段，当前加载路径未见针对这些旧字段的转换器。按默认反序列化路径，旧筛选字段会被忽略，动态单位退化到默认选取，旧 `HealthName` 不再建立相应数值；计数筛选同样丢失。[S2]

此外，1.2.1.28 的驱散类型由已学技能表筛选；当前 `UpdateSpellKnown` 改为启用全部已列类型。原 JSON 的意图应以历史实现解释，当前版本用于指出差异，不能混用。[S5]

## 2. Shigure 实际执行链

```text
插件状态、队伍色块、充能条、治疗吸收条
  → 像素解码和 StateBuilder
  → 提前计算被筛选器引用的动态阈值
  → 解析动态单位及其生命值字段
  → 计算人数
  → 应用其余数值调整
  → 从上到下判断规则
  → 解析单位、技能名称和宏键位
  → 返回本轮动作或暂停
```

### 2.1 规则判断

- 本文件 40 条规则中 39 条启用，只有 R14 禁用；没有设置 `ContinueLogic`，命中后默认结束本轮。
- `Condition` 与 `SubConditions` 的关系为：`主条件 AND (子条件1 OR 子条件2 …)`。例如 R23 为 `输出最低值≤80 AND 战斗中 AND 美德就绪 AND (C90≥3 OR C80≥2)`。
- 空主条件为真，但 R06 是特殊动作；没有插入技能、没有技能映射或冷却未就绪时会跳过，并非无条件挡住后续规则。
- 动态单位没有候选时跳过对应动作。未解析数值的大小比较不命中；不是把缺失生命值当成 0。
- 条件解析出错会结束本轮并返回错误。子条件按顺序求值，先命中就短路；只有实际被求值的错误才会影响本轮。
- 普通动作命中后即使查不到热键，也可能返回空热键决策并结束本轮，不等于“这条没放出来就继续找下一个”。规则也没有自动检查所有动作的圣能、移动和射程。[S1]

Shigure 的外层“有效性”主要排除死亡、骑乘、输入、饮水、坐骑读条等；并不统一禁止普通治疗读条期间计算规则。JSON 只在 R07 暂停引导，R01–R06 仍在它之前。PixHoly 则会在任何施法、引导或蓄力时直接 Idle，并且脱战只补圣言祭礼。两者不能直接套用同一组入口判断。[S6][P3]

### 2.2 单位、职责与首领编码

| 数据 | 真实含义 |
| --- | --- |
| 动态单位槽 1–5 | 小队中依次为 player、party1、party2、party3、party4；单人时槽 1 仍为 player |
| `Unit=0` 或省略 | 不指定宏目标；通常交给普通技能宏，不能解释成固定 target 单位槽 |
| `Unit=41 / 42 / 45` | 玩家 / 当前目标 / 鼠标指向 |
| 职责 1 / 2 / 3 | 坦克 / 治疗 / 输出；显式职责 0 被选择器排除 |
| `目标类型` 1–100 / >100 | 可攻击 / 可协助的单位身份编码；它不是 NPC ID |
| `目标类型=146` | 可协助且身份为 boss1：100 + 46，不是固定 NPC 编号 |
| `首领战=92` | 映射 encounter 3201，源码注释“护光者鲁伊亚” |
| `首领战=100` | 映射 encounter 2623，源码注释“基拉卡与厄克哈特·风脉” |
| `首领战=107` | 映射 encounter 2127，源码注释“塞塔里斯的化身” |

职责色块还承担资格过滤：死亡、不可协助、临时失去视线、超出 `UnitInRange` 范围等会使其输出 0；27827 光环覆盖槽也会把职责置 0。C# 层不是完整的存在性验证器，职责缺失或无法解析不一定被排除。迁移不能只复制 `role != 0` 而遗漏上游资格判断。[S3][S4]

`目标距离` 来自 LibRangeCheck 范围估算；不能把它当精确距离。首领施法正计时使用 `castCurve`：25.5 秒映射为 255，故 R04/R05 的 40 是约 4 秒，不是进度百分比，也不是 40 秒。[S4]

### 2.3 血量、吸收、光环和冷却口径

**队伍生命值不是纯当前生命百分比。** `UnitHealthPercent(unit, true, curve)` 先输出预测生命值；默认曲线约为 0–100。玩家向某队友读圣光术时，该队友改用加 40 的曲线；圣光闪现改用加 15 的曲线。随后 `StateBuilder.BuildGroup` 从此数值扣除治疗吸收条解出的数值，并保留 0 和负数。[S3]

可按以下公式理解原比较值，但各项均包含原像素量化：

`H = 编码后的预测生命百分数（含本地治疗估算偏移） - 编码后的治疗吸收百分数`

治疗吸收条使用 `UnitGetDetailedHealPrediction → calculator:GetHealAbsorbs()`，上限取 `GetMaximumHealth()`。因此吸收字段是相对于最大生命的百分比刻度，不是绝对治疗量；计算器结果还受其模式、治疗抵扣和钳制影响，不宜叫作“原始总吸收”。官方客户端 API 声明也明确区分计算后的吸收与钳制标记。[S3][W1]

原选择器允许有效单位的 H≤0，人数计数中的 `PositiveHealthOnly=true` 却只统计 H>0。重度吸收单位可能被选为最低，但不进入 C90/C80/C70。这是源码可确认的行为，不应擅自解释成死亡单位。

| 字段 | 原单位与重要歧义 |
| --- | --- |
| 玩家 `生命值` | 玩家预测生命百分数；不像队伍 H 那样在 StateBuilder 中扣除队伍吸收 |
| `法力值` | 百分数，通常 0–100 |
| `神圣能量` | 圣能整数；本文件会在读条时临时加 1，不是已经获得的资源 |
| `auras.player.ID.value` | 剩余秒数，约 1 秒一档；存在但不足 1 秒仍至少显示 1，永久光环为 255；不是层数 |
| `auras.player.ID.applications` | 独立层数字段；本文件没有引用 |
| `spells.ID.cooldown` | 剩余秒数刻度；原插件排除仅由 GCD 引起的阻塞，未知或不可用不是 0 |
| `spells.20473.count` | 当前充能数，不是施放累计次数 |
| `spells.20473.chargeCooldown` | 下一层充能恢复的剩余秒数，与普通冷却分开 |
| `治疗药水` | 依赖中 item 241304 的剩余冷却；0=有库存且冷却就绪，255 也可表示缺失或不可用 |
| `施法技能`、`插入法术` | 底层像素为本地技能索引；条件求值时把右侧 spell ID 转成索引后比较 |

上述秒数、百分数和 ID 转换来自源码，而不是根据中文字段名猜测。[S1][S4][S5]

### 5.3 需要评审的行为，不直接判为错误

- 原规则驱散优先于药水和圣疗。极低血量同时有可驱散目标时，先驱散；是否调整属于治疗策略决定。
- R21可以在轻度缺血、存在敌对近战目标时提前消耗圣能；R22又早于道标和鸣钟。是否符合预期需回放，不能根据一般治疗经验擅自重排。
- R23/R24硬性要求有符合血量的输出职责成员。只有坦克/治疗受伤时可能不触发，尽管人数条件达到要求。
- 原驱散像素只展示一个按到期时间排序的匹配光环类型，不是类型集合。多个减益并存时，另一个类型可能被遮住；当前版本还允许不一定能处理的类型参与竞争。迁移成Magic/Disease/Poison三格会改变可观察信息，属于明确改进，非逐像素等价。[S5]
- 缺少常规读条移动保护、圣疗限制检查、每技能射程与技能可用性检查时，前排命中动作可能持续失败。需要在迁移实现时补齐，但目前未在游戏内复现这些失败。
- R04/R05没有验证具体技能，R36–R39顺序较低；首领名称、身份编码成立不等于战术正确。
- GCD处理、1秒冷却档、光环1秒最小值与 PixHoly 的小数曲线不同；在临界帧可能产生不同动作，必须列为可接受或需修正的差异。

## 6. 五人状态与像素协议建议

### 6.1 职责分工与最小数据接口

建议在 `pix/context.py` 中增加一个固定五人视图，例如 `PartyMember` 和 `ctx.party`，只表示 player、party1–4。存在性和有效性必须独立于血量：死亡或缺失单位不可入选，但有效生命值为0/负数的存活单位仍可能需要治疗。没有候选返回 `None`，不能回退成玩家。[P1]

建议的语义字段：`unit_token`、`exists`、`alive`、`connected`、`can_assist`、`role`、`health_pct`、`heal_absorb_pct`、`effective_health_pct`、三类驱散标记，以及实际技能的射程状态。每字段必须可区分无效采样与业务零值；`connected` 在本地技能中没有现成示例，需另行核对API和秘密值行为后接入，不冒称技能已覆盖。

选择器和计数在 Python 使用同一快照计算；Lua只通过允许的显示消费者输出属性，不在 Lua 中比较秘密血量以选最低队友。C90等派生量、三个阈值和目标选择无需另占像素。

### 6.2 曲线、量化与无效值

PixHoly现有曲线可复用：[P1][P2]

- 冷却秒数 `0/10/30/120/245` 对应亮度 `255/155/115/25/0`，0–10秒段每级0.1秒。黑色可能未知或超上限，白色才接近就绪端。
- 光环秒数 `0/15/30/60/240` 对应亮度 `0/150/180/210/255`，0–15秒段每级0.1秒；它与原版约1秒档有差异。
- 保留4×4 Cell、8×8 IconTile和12px高基板。现有Cell读内部2×2区域、平均RGB，故新格应输出R=G=B；直接把Shigure“R/G索引、B数值”的色块拷过来会读错。
- 100px吸收条内容区可用现有 `ValueBar:New(x,25)`，连分隔共26个Cell=104px。五条共520px。排除红色分隔，白黑分母为0应无效；现有 `ValueBar.ratio` 此时返回0，需要在接入时修正有效性处理。
- 原Shigure吸收条还有单位索引、渐变底和端点标记；更换成普通黑白比例条是重新编码，不承诺每像素完全相同。饱和时保留“达到上限”状态，不能声称能恢复任意绝对吸收量。
- 对R30的一秒边界、H=80/90和冷却=0，验收应分别覆盖边界前后；不为掩盖量化差异悄悄加容差。初版按解码值比较，并记录与原版整数档的差异。

建议缺失/异常/过期数据采用显式无效状态，受影响的规则不执行；有些公共资格数据失效时整轮Idle。现有 `readBooleanCell` 把所有非白色当false、计数取均值等捷径，不足以承担奶骑“有效目标”的完整契约。

35个定向动作对应七个射程ID所代表的动作；其他动作是否加入取决于评审结果。用已有键盘驱动支持的键名与项目既有宏模式，不直接复制Shigure 1143组合表。Lua和Python键表必须一一对应，队伍变动不能让已计算的party2误指向新成员。首版可在成员重绑时短暂输出无效状态，等待新完整帧，再恢复决策。

成员连通性、视线和施法失败反馈是现有能力缺口。原Shigure会把观察到的失去视线目标暂时排除1.5秒；PixHoly目前没有相应反馈链路。不要把“射程内且存活”写成“保证能施法”，也不要在没有失败证据时造一个固定超时黑名单。[S3][P3]

## 8. 实施阶段与验收场景

### 8.1 建议实施顺序

1. **数据与观察**：确定奶骑字段、专精门控和五人单位映射；仅显示与解码，不发送按键。先验收血量、吸收、职责、驱散及充能；明确治疗吸收的饱和与有效生命边界。
2. **通用治疗核心**：接入R07–R13、R19–R35、R40，R14继续禁用；先完成驱散/药水标识修正和施法保护，再按原优先级回放。R21若要降级到最后填充，必须作为独立策略变更记录，不能夹带在翻译中。
3. **读条预测**：验证施法ID和目标识别、长读条、取消、失败、同名目标以及成员变动，再决定是否恢复V01/V02及+15/+40估算。技能的cast-target示例有每秒清空和秘密目标名暂留等限制，不能直接充当可靠长读条目标。[K1]
4. **首领与手动插入**：分别评估R01–R06、R15–R18、R36–R39；确认数据、具体技能和顺序后再接入。没有安装/没有识别时不命中，不依赖伪造首领编码。
